## ۱. آسیب‌پذیریِ وابستگی: `certifi` (PYSEC-2026-4320)

**شدت:** HIGH · **وضعیت:** ✅ رفع‌شده

`requirements.txt` نسخهٔ `certifi==2026.7.22` را قفل کرده بود که در برابر
PYSEC-2026-4320 آسیب‌پذیر است. چون وابستگی‌ها **دقیق** قفل شده‌اند، به‌روزرسانی
باید صریح و مستند باشد:

```diff
-certifi==2026.7.22
+certifi==2026.10.18
+# certifi 2026.10.18 — رفع PYSEC-2026-4320 (گیتِ pip-audit در CI).
```

راستی‌آزمایی (خروجیِ واقعی):

```
$ pip-audit -r requirements.txt --no-deps
No known vulnerabilities found
```

این گیت حالا در CI هم اجرا می‌شود (`DEVOPS-05`) ⇒ یک CVEِ تازه، build را قرمز
می‌کند.

## ۲. D-3 — مسیرِ دیتابیس: از bind-mount به حجمِ ماندگار

**شدت:** MEDIUM · **وضعیت:** ✅ رفع‌شده

### مسئله

در چیدمانِ قبلی، پوشهٔ کدِ میزبان به `/app` داخلِ کانتینر mount می‌شد و
دیتابیس کنارِ همان کد (یعنی داخلِ همان مسیرِ mount‌شده) قرار داشت. نتیجه:

* بکاپ‌گیری از دیتابیس به مسیرِ «کد» گره خورده بود؛
* با `docker compose up --force-recreate` یا هر تغییرِ چیدمان، دیتابیس در معرضِ
  جابه‌جایی/پاک‌شدن بود؛
* مسیرِ دیتابیس داخلِ کانتینر (`/app/newsbot.db`) با مسیرِ واقعیِ روی میزبان فرق
  داشت ⇒ هر ابزارِ بکاپ باید نگاشت را بلد می‌بود.

### اصلاح

| لایه | مقدارِ جدید |
|---|---|
| روی میزبان | `/opt/newsbot-data/newsbot.db` (+ `-wal`/`-shm` و پوشهٔ `backups`) |
| داخلِ کانتینر | `/app/data/newsbot.db` (روی حجمِ ماندگارِ `/opt/newsbot-data:/app/data`) |
| در Compose | `DB_FILE: /app/data/newsbot.db` |
| در ایمیج | `ENV DB_FILE=/app/data/newsbot.db` |
| در اسکریپت | `migrate_db_path`: انتقالِ امن (همراه `-wal`/`-shm` و آرشیو)، با حفظِ مالکیتِ uid 10001 و توقفِ کار در صورتِ خطا |

اسکریپتِ استقرار **قبل از بازساختِ کانتینر** این مهاجرت را انجام می‌دهد و اگر
شکست بخورد، deploy متوقف می‌شود (هیچ داده‌ای جابه‌جا نمی‌شود).

### اثر بر منطقِ کسب‌وکار

* بکاپِ `sqlite3.backup` حالا همیشه از همان فایلی گرفته می‌شود که سرویس واقعاً
  استفاده می‌کند (`/opt/newsbot-data/newsbot.db`).
* کانتینر با `read_only: true` بالا می‌آید ⇒ نوشتنِ دیتابیس فقط از مسیرِ حجمِ
  ماندگار ممکن است ⇒ یک خطای پیکربندی (مثل DB اشتباه) *بلافاصله* در healthcheck
  دیده می‌شود، نه بعد از ساعت‌ها.

## ۳. رازها و مجوزها

**وضعیت:** ✅ حفظ و تقویت شد

* توکنِ ربات و کلیدهای AI هرگز داخلِ ایمیج نمی‌روند: `docker-compose.yml` آن‌ها
  را از `/etc/newsbot/env` (خارجِ ایمیج) می‌خواند و `.dockerignore` هم `.env` را
  از contextِ build حذف کرده است.
* فایلِ env باید `mode 600` و متعلق به root باشد (در `docs/VPS_DEPLOYMENT.md`
  مستند شده). کانتینر با کاربرِ غیرroot (uid 10001) اجرا می‌شود.
* healthcheck عمداً **بدونِ توکن** است (`newsbot/healthcheck.py`): فقط import،
  نوشتن‌پذیریِ پوشهٔ داده و یک `SELECT 1` روی دیتابیس. یعنی اجرای آن هیچ رازی
  را در اختیارِ کسی نمی‌گذارد و در لاگ هم چیزی نشت نمی‌دهد.
* `.env.example` هم‌راستا با `newsbot/config.py` باقی است و تستِ
  `tests/test_phase12_config_docs.py` آن را تضمین می‌کند (بخش ۰۱).

## ۴. اثرِ تخلیهٔ ایمن بر منطقِ انتشار (DEVOPS-08)

**وضعیت:** ✅ رفع‌شده

مهم‌ترین اثرِ کسب‌وکاریِ این فاز: **انتشارِ نیمه‌کاره**. مسیرِ
`reserve_publication → send → ack` در ژورنال (`pub_journal`) وضعیتِ مقاله را
نگه می‌دارد؛ اگر پروسه وسطِ همین مسیر بمیرد، مقاله در `delivery_unknown`
می‌ماند و بعداً به آن رسیدگیِ دستی لازم است.

با دروازهٔ تخلیه:

| مرحله | رفتارِ جدید |
|---|---|
| شروعِ انتشار (`publish.py`) | اگر تخلیه فعال است، اصلاً رزروِ ژورنال انجام نمی‌شود ⇒ نتیجه `"draining"` (نه مقالهٔ نیمه‌کاره) |
| انتشارِ در حالِ پرواز | تا پایان ادامه می‌یابد (شمارندهٔ `in_flight`) |
| پایان | `end_publish()` در `finally` ⇒ حتی با لغو/خطا، شمارنده درست می‌شود |
| چرخهٔ کانال (`cycle.py`) | با `"draining"` متوقف می‌شود ولی **بقیهٔ صف دست‌نخورده** می‌ماند ⇒ بعد از استقرار منتشر می‌شود |
| زمان‌بند (`scheduler.py`) | تیکِ تازه شروع نمی‌شود؛ تیکِ در حالِ اجرا تمام می‌شود |

پس از استقرار، رباتِ تازه همان صف را از همان‌جا ادامه می‌دهد.

## ۵. یکپارچگیِ دیتابیس پس از استقرار

پس از هر استقرار، این بررسی‌ها باید سبز باشند:

```bash
docker exec bot-official-telegram python -m newsbot.healthcheck
docker inspect bot-official-telegram --format '{{.State.Health.Status}}'
ls -l /opt/newsbot-data/            # newsbot.db + -wal/-shm، مالکِ uid 10001
sqlite3 /opt/newsbot-data/newsbot.db "SELECT value FROM meta WHERE key='schema_version';"
```

مهاجرتِ اسکیما همچنان خودکار است (نسخهٔ اسکیما در `newsbot/__init__.py` است و
buildِ جدید هنگامِ استارت آن را اعمال می‌کند) و downgradeِ اسکیما رد می‌شود.
