# Phase 4 — Reply-to-channel-post Q&A core (design)

**تاریخ:** 2026-11-14 · **وضعیت:** تأییدشده توسط مالک · **فاز:** ۴ از ۱۰

---

## 1. هدف و چرا

کاربر در **گروهِ بحثِ کانال** به یک پستِ منتشرشده reply می‌کند و انتظار دارد ربات به سؤالش دربارهٔ **همان پست** پاسخ بدهد. امروز ربات فقط پیام‌های چتِ خصوصی را می‌گیرد (`newsbot/app.py:274`)؛ هیچ مسیری برای گروه وجود ندارد.

فاز ۴ هستهٔ این قابلیت را می‌سازد: **پاسخ‌دادن به سؤالِ replyشده، با کنترلِ زمینه (فقط متنِ همان پست) و تحویلِ idempotent (هر پیام فقط یک پاسخ).**

## 2. هدف‌ها / غیرهدف‌ها / ضدهدف‌ها

**هدف‌ها**
- G1: پیامِ replyشده به پستِ کانال ⇒ یک پاسخِ کوتاه که فقط از متنِ همان پست ساخته شده.
- G2: زمینهٔ ورودی **محدود و کنترل‌شده** است: متنِ پست + متنِ سؤال، هر دو با سقفِ طول.
- G3: تحویل **exactly-once**: تحویلِ دوبارهٔ همان update (ری‌استارت، قطعِ شبکه، `concurrent_updates`) هیچ پاسخِ دومی نمی‌سازد.
- G4: گروه‌های نامرتبط **سکوت** می‌کنند — ربات در هیچ گروهی که به کانالِ ثبت‌شده وصل نیست چیزی نمی‌نویسد.

**غیرهدف‌ها (در فازهای بعدی)**
- سهمیه/کوoldown/سقفِ روزانهٔ هر کاربر ⇒ **فاز ۵**.
- نمایشِ `typing` ⇒ **فاز ۶**.
- onboarding / مسیریابیِ پیام / منوی خانه ⇒ **فاز ۷**.
- deeplink «بازگشت به کانال» ⇒ **فاز ۸**.

**ضدهدف‌ها (چیزی که فاز ۴ را بی‌ارزش می‌کند)**
- پاسخ‌دادن از دانشِ عمومیِ مدل به‌جای محتوایِ پست ⇒ محدود به متنِ پست.
- جواب‌دادن در گروه‌های غریبه ⇒ سکوت.
- پاسخِ تکراری به‌خاطرِ redelivery ⇒ claimِ اتمیک.

## 3. قیدها

- گزارش‌ها و متنِ UI فارسی؛ شناسه‌های فنی انگلیسی.
- هیچ secret در کد/لاگ/PR/artifact.
- هر تغییرِ رفتار یا اسکیما ⇒ تست.
- `SCHEMA_VERSION` یکی بالا می‌رود (۱۱ → ۱۲).
- DB backend: sqlite و D1 هر دو باید کار کنند.

## 4. رویکردهای بررسی‌شده

| # | رویکرد | مزیت | عیب | نتیجه |
|---|---|---|---|---|
| A | متنِ پست از خودِ `reply_to_message` (فورواردِ خودکارِ تلگرام) | بدونِ APIِ اضافه، بدونِ ستونِ `message_id`، بدونِ backfill؛ برای پست‌های قدیمی هم کار می‌کند | فقط متن/کپشن را می‌دهد (نه فایل‌های پیوست) | **انتخاب‌شده** |
| B | ذخیرهٔ هر پستِ منتشرشده با `message_id` در DB | زمینهٔ کامل‌تر (می‌توان HTML پست را داد) | فقط برای پست‌های آینده معتبر است، نیازمندِ ستون + backfill + مهاجرت | رد شد |
| C | گرفتنِ پستِ اصلی از کانال با API (`copyMessage`/`forward`) | متنِ کاملِ کانال | یک تماسِ شبکهٔ اضافه به‌ازای هر سؤال + نیاز به دسترسیِ مدیرِ کانال | رد شد |

نگاشتِ «گروه ← کانال»: **خودکار** از `sender_chat`/`forward_from_chat` پیامِ replyشده (که خودِ کانالِ پست را می‌گوید) به‌علاوهٔ تأییدِ لینکِ گروه با `get_chat(...).linked_chat_id` که کش می‌شود. گزینهٔ «تنظیمِ دستیِ آیدیِ گروه» رد شد: صفر-کانفیگ است و مالک را معطل نمی‌کند.

## 5. طراحی

### 5.1 جریان

```
update (گروه) → on_group_reply
  ├─ reply_to_message ندارد؟ → سکوت
  ├─ پستِ کانال شناسایی نشد؟ → سکوت
  ├─ گروه به کانالِ دیگری لینک است؟ → سکوت
  ├─ claim در qa_answers (INSERT OR IGNORE) → اگر تکراری بود → سکوت
  ├─ ساختِ prompt (پست + سؤال، هر دو کوتاه‌شده)
  ├─ ai_chat(system, user) → پاسخ / خطا
  ├─ ارسال: reply به پیامِ کاربر در همان گروه (plain text)
  └─ به‌روزرسانیِ رکورد: answered | failed (+ متنِ خطای کوتاه)
```

### 5.2 تشخیصِ «پستِ کانال»

پیامِ replyشده در گروهِ بحث یک **automatic forward** از کانال است:
- `reply.sender_chat.type == "channel"` و `reply.sender_chat.id` ⇒ نامزدِ کانال؛
- یا `reply.forward_from_chat` (فورواردِ دستی) ⇒ همان نامزد.

نامزد با `channel_by_chat(chat_id)` به کانالِ **ثبت‌شده** نگاشت می‌شود؛ نبود ⇒ سکوت.

تأییدِ گروه: `linked_chat_id` از `bot.get_chat(group_id)` (کش‌شده در جدول `kv_cache` با کلیدِ `qa:linked:<group_id>`، عمرِ ۶ ساعت).
- `linked_chat_id` ناموجود/ناخوانا ⇒ **fail-open** (پست خودش ثابت می‌کند از کانالِ ما است؛ ربات فقط در گروهی است که عضو است).
- `linked_chat_id` موجود ولی ≠ کانال ⇒ سکوت.

### 5.3 زمینهٔ کنترل‌شده

- متنِ پست: `reply.text` یا `reply.caption`؛ حذفِ HTML (`strip_tags`) و بریدن به `config.QA_CONTEXT_MAX_CHARS` (پیش‌فرض ۴۰۰۰).
- متنِ سؤال: `message.text`/`caption`، بریده به `config.QA_QUESTION_MAX_CHARS` (۱۰۰۰).
- اگر پست متن ندارد ⇒ پاسخِ صادقانهٔ ثابت («این پست متنی ندارد…») بدونِ تماسِ AI.
- پاسخ نهایی بریده به `config.QA_ANSWER_MAX_CHARS` (۹۰۰) و به متنِ ساده تبدیل می‌شود (بدونِ Markdown/HTML).

### 5.4 فراخوانیِ AI

`ai_chat(system, user)` — همان دروازهٔ فاز ۲/۳: سهمیهٔ روزانه، failover، و **چرخشِ round-robin** (فاز ۳) خودکار اعمال می‌شود. `owner_id=None` ⇒ استخرِ عمومی.
System prompt صریحاً می‌گوید: فقط از متنِ پست استفاده کن، اگر پاسخ در پست نیست صادقانه بگو، هم‌زبانِ سؤال جواب بده، حداکثر ۴ جمله، متنِ ساده.

### 5.5 تحویلِ idempotent

جدولِ جدید (اسکیمای v12):

```sql
CREATE TABLE IF NOT EXISTS qa_answers(
  chat_id INTEGER, msg_id INTEGER, user_id INTEGER, channel_id INTEGER,
  status TEXT DEFAULT 'pending',   -- pending | answered | failed
  answer TEXT DEFAULT '', error TEXT DEFAULT '',
  created_at TEXT, updated_at TEXT,
  PRIMARY KEY(chat_id, msg_id)
);
CREATE INDEX IF NOT EXISTS idx_qa_answers_user ON qa_answers(user_id);
```

- **claim**: یک دستورِ اتمیکِ `INSERT OR IGNORE` (روی sqlite و D1 هر دو تک‌دستوره و اتمیک است). `rowcount == 0` ⇒ این پیام قبلاً claim شده ⇒ سکوت (حتی اگر وضعیتش `failed` باشد: تحویلِ دوباره هم پاسخِ دوم نمی‌سازد).
- **نتیجه**: `UPDATE qa_answers SET status='answered', answer=?` یا `status='failed', error=?`.
- `msg_id` کلیدِ یکتاست ⇒ «یک پیامِ کاربر ⇒ یک پاسخ» حتی با پردازشِ هم‌زمان.

### 5.6 خطا

- خطای AI/شبکه ⇒ یک پیامِ کوتاهِ صادقانه («فعلاً نتوانستم پاسخ بدهم») **یک‌بار** + ثبتِ `failed`. پیامِ دوم (redelivery) سکوت.
- استثنای ناشناخته ⇒ لاگ (بدونِ متنِ پست/سؤال) و رکوردِ `failed`.

### 5.7 لاگ و secret

لاگ فقط شناسه‌ها و طول‌ها را می‌گوید (`group=%s msg=%s ctx=%d`), نه متنِ پست/سؤال، نه token.

## 7. تست‌ها (TDD — اول قرمز)

1. reply به پستِ کانال ⇒ یک پاسخ، با `reply_to_message_id` درست.
2. prompt فقط شاملِ متنِ پست + سؤال (با سقفِ طول).
3. reply به پیامِ عادیِ کاربر ⇒ سکوت.
4. گروهِ لینک‌شده به کانالِ دیگر ⇒ سکوت.
5. تحویلِ دوبارهٔ همان پیام ⇒ دقیقاً یک پاسخ.
6. دو پردازشِ هم‌زمانِ یک پیام ⇒ یک پاسخ.
7. خطای AI ⇒ یک پیامِ خطا، بدونِ crash، رکورد=`failed`.
8. پستِ فقط‌مدیا (بدون متن) ⇒ پاسخِ صادقانه، بدونِ تماسِ AI.
9. پستِ خیلی بلند ⇒ زمینه بریده می‌شود.
10. پاسخِ خیلی بلند ⇒ بریده می‌شود.
11. پیامِ گروه بدونِ reply ⇒ سکوت.
12. لاگ متنِ پست/سؤال را نشت نمی‌دهد.
13. `app.py` هندلرِ گروه را ثبت می‌کند (نگهبانِ ثبت).
14. اسکیما: جدول و ستون‌های `qa_answers` وجود دارند؛ `tools/migrate_sqlite_to_d1.py` آن را حمل می‌کند.
15. D1: همان اسکیما روی مسیرِ D1.

## 8. پیش‌نیازِ سمتِ مالک (B-4)

ربات باید **عضوِ گروهِ بحث** باشد. اگر عضوِ عادی باشد ⇒ Privacy Mode باید در BotFather خاموش شود؛ اگر **ادمینِ گروه** باشد، خاموش‌کردن لازم نیست. بدونِ این، هیچ پیامی به ربات نمی‌رسد و مسیرِ گروه قابلِ تستِ واقعی نیست.
