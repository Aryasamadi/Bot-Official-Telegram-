# سند تصمیم D1 — تصمیم ۲-الف: ماندن روی SQLite و بستن مسیر D1

**وضعیت: قطعی (لازم‌الاجرا) — بازنگری فقط با تصمیم صریح جدید کاربر.**
**فاز اجرا: ۱۱ (کیفیت داده — مسیر D1) · تاریخ ثبت: ۲۰۲۶-۱۰-۱۷**

## تصمیم

منبع رسمی و تنها مسیر پشتیبانی‌شدهٔ داده، **SQLite** است. مسیر **Cloudflare D1 به‌عنوان
بک‌اند رسمی رد می‌شود** و `DB_BACKEND=d1` یک مسیر **غیررسمی/غیرپشتیبان** باقی می‌ماند:

- هیچ استقرار تولیدی نباید با `DB_BACKEND=d1` اجرا شود.
- ابزارهای `tools/migrate_sqlite_to_d1.py` و `tools/restore_d1_to_sqlite.py` فقط برای
  **بکاپ/آینهٔ دستی و مهاجرت آزمایشی** باقی می‌مانند (پروتکل عملیاتی: بخش ۵.۱ در
  `docs/DEPLOY_RUNBOOK.md`).
- تمام مسیرهای نوشتن بحرانی روی SQLite داخل یک تراکنش `_trx` (یا تک‌دستورِ CAS) اتمیک‌اند؛
  گارد پیش‌پرواز/استارت در `db.py` از فعال‌سازی ناخواستهٔ D1 جلوگیری می‌کند.

## چرا

۱. آداپتر D1 (REST) تراکنش تعاملی ندارد، هر `execute()` یک درخواست شبکه است و حلقهٔ
   رویداد asyncio را بلاک می‌کند (ریسک پاسخ‌گویی و هزینهٔ درخواست).
۲. الزامات اتمیک‌سازی روی D1 (batch، retry/backoff، قفل بین‌پروسه، idempotency، audit log)
   بدون یک لایهٔ async/outbox جدید قابل تضمین نیست — هزینه و ریسک آن برای مقیاس فعلی توجیه ندارد.
۳. روی SQLite همهٔ این ریسک‌ها در فازهای ۱–۱۰ با تراکنش‌های واحد و تست‌ها بسته شده‌اند.

## چک‌لیست بازگشایی مسیر D1 (فقط اگر کاربر بعداً تصمیم مهاجرت بگیرد)

۱. آداپتر async یا صف نوشتن پایدار (outbox) به‌جای `httpx.Client` همگام.
۲. قفل بین‌پروسه‌ای/توزیع‌شده برای D1.
۳. اتمیک‌سازی ۴ سایت چند-دستوری (بالا) + idempotency و روال جبران.
۴. جدول audit log و ترتیب‌بندی/ریت‌لیمیت درخواست‌ها (batch).
۵. اجرای کامل تست‌ها **روی یک D1 واقعی** (شبیه‌سازی کافی نیست) + تست مهاجرت نمونه.

> تا زمان اجرای این چک‌لیست، `DB_BACKEND=d1` تنها برای آزمایش دستی مجاز است؛
> کشف هر رفتار جدید روی این مسیر به‌معنای بازگشایی همین سند است، نه پذیرش D1.
